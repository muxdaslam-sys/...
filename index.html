1. Project Overview & Clean N-Tier Architecture Core

How to deliver an authoritative project pitch and explain the backend architectural boundaries.

Q1: Can you give a 2-minute overview of VitalQ and the core problem it solves? Architecture

Strong Answer to deliver:

"VitalQ is a real-time hospital Outpatient Department (OPD) queue orchestration platform built using ASP.NET Core 8 Web API, Angular 19, SignalR WebSockets, and Microsoft SQL Server.

In conventional hospitals, OPD waiting rooms suffer from two major problems:

  1. Blind Waiting: Patients hold physical paper slips with zero visibility into queue movement, leading to crowded hallways and constant interruptions at doctor consultation doors.
  2. First-Come-First-Serve (FIFO) Danger: Critical emergency patients (such as severe hypoxia or acute chest pain) are forced to wait behind routine checkups because traditional queues do not factor in clinical acuity.

2. Real-Time WebSockets & SignalR Architecture SignalR

Deep-dive technical questions on multi-room routing, reconnection policies, and event push.

Q3: Why did you choose SignalR over HTTP Polling or Server-Sent Events (SSE)? SignalR

"In high-volume hospital OPDs with hundreds of active patients tracking tickets, polling every 3–5 seconds creates massive database overhead, flooding SQL Server with redundant SELECT queries where 95% of calls return identical data.

Server-Sent Events (SSE) is unidirectional (server to client only). While lightweight, it lacks native bi-directional client negotiation and automatic transport fallback.

SignalR was the best architectural choice because:

  • It establishes a persistent, duplex WebSocket connection, reducing network traffic and latency by over 95%.
  • It natively supports Group Targeting (Rooms), allowing targeted broadcasts exclusively to specific rooms rather than blasting the entire hospital.
  • It provides graceful transport fallback (WebSockets → Server-Sent Events → Long Polling) for older hospital terminals or restrictive proxy firewalls.
Q4: How does your SignalR multi-group routing work across all 4 modules? SignalR

"In QueueHub.cs, clients do not listen to a single global channel. Instead, I structured targeted SignalR rooms:

  • doctor-{doctorId}: Subscribed to by the doctor console, and also by all patients waiting in that doctor's line.
  • patient-{tokenId}: Subscribed to by the individual patient holding that token slip (for audio summons and room alerts).
  • nurse-station: Subscribed to by triage nurses to receive new walk-in bookings and doctor availability toggles.
  • admin-dashboard: Subscribed to by administrators for real-time aggregated KPI counts.

When a doctor calls a patient via NotifyPatientCalledAsync(token):

  1. The summoned patient in patient-{tokenId} receives PatientCalled (triggers audio chime and flashing screen).
  2. The doctor room doctor-{doctorId} receives QueueUpdated, causing all subsequent patients in line to decrement their 'Patients Ahead' count immediately.
  3. The admin-dashboard receives QueueUpdated to refresh queue metrics silently without a page reload.
Q5: How do you handle JWT authentication inside SignalR, and what happens when hospital Wi-Fi drops? SignalR & Security

"Standard browser WebSockets do not support custom HTTP Authorization headers during the initial WebSocket handshake.

To solve this, in Program.cs, I configured the JWT Bearer authentication options to read the access token from the query string context.Request.Query['access_token'] whenever the request path starts with /hubs/queue.

The Critical Reconnection Resilience Fix:
If a triage nurse or doctor experiences an intermittent hospital Wi-Fi disconnect, SignalR automatically reconnects using withAutomaticReconnect([0, 2000, 5000, 10000, 30000]).

If you pass a static token string, reconnecting 30 minutes later transmits an expired token, causing an unrecoverable 401 Unauthorized socket drop. In signalr.service.ts, I implemented a dynamic lambda factory:

this.hubConnection = new signalR.HubConnectionBuilder() .withUrl(environment.signalrUrl, { // Dynamic factory lambda: evaluates latest rotated JWT from storage on EVERY reconnect! accessTokenFactory: () => localStorage.getItem('vq_token') || '' }) .withAutomaticReconnect() .build();

This ensures that even after a connection drop, the freshly refreshed JWT is transmitted during the re-handshake."

Q6: What was the case-normalization bug in your SignalR groups? Debugging

"In early testing, some doctor queue notifications were randomly dropping. I debugged the SignalR hub and discovered a subtle case-sensitivity mismatch:

When a doctor logged in, the Angular client joined doctor-a3f89b... (lowercase GUID string from route params). However, the backend notification service was constructing the group name via $"doctor-{token.DoctorId}", which ASP.NET Core formatted in uppercase doctor-A3F89B... on certain OS environments.

Because SignalR group names are string-matched with case-sensitivity, the messages were silently routed into an empty room!

Fix: I enforced strict .ToLowerInvariant() normalization on both the backend hub methods and the frontend client service, ensuring 100% reliable group subscriptions."

3. Consultation Pacing & Absentee Engine Doctor Module

Q7: How did you fix the '+333m Overtime' consultation stopwatch bug? Timezone Engineering

"In our initial doctor console, when a doctor called a patient, the consultation duration timer suddenly jumped to +333m Overtime instead of starting at 0:00.

Root Cause: The SQL Server database saved CalledAtUtc as a UTC string without an explicit trailing 'Z' (e.g. 2026-10-21T10:00:00). When the browser in India (IST, UTC+05:30) passed this string to new Date(calledAtUtc), JavaScript defaulted to parsing it as local IST instead of UTC, causing an artificial 5-hour 30-minute (330-minute) offset!

Solution: I engineered a bulletproof helper function parseUtcTimestamp(raw):

export function parseUtcTimestamp(raw: string | null | undefined): number { if (!raw) return Date.now(); // Ensure trailing 'Z' is present so browser JavaScript strictly evaluates it as UTC! const utcString = raw.endsWith('Z') ? raw : `${raw}Z`; return new Date(utcString).getTime(); }

Now, the timer strictly measures (Date.now() - calledAtUtc) in UTC milliseconds, accurately starting at 0:00 for every patient."

Q8: Explain your 3-Strike Absentee & No-Show protocol. Business Logic

"In busy OPDs, patients frequently wander to the pharmacy or canteen. When their number is called and they are absent, doctors previously had only two bad choices: hold up the entire line waiting for them, or delete the ticket permanently.

I engineered an automated 3-Strike Absentee Engine:

  • Strike 1 & 2 (Hold Queue): When a doctor clicks 'Skip', an in-app confirmation modal warns the doctor of the patient's strike count. Upon confirmation, the patient's status transitions to Skipped, incrementing SkipCount, and moves to an on-hold tray. The doctor immediately calls the next patient without delay.
  • Strike 3 (Automatic Expiry): If a patient is skipped a 3rd time, the system automatically transitions their token to Expired with an audit log reason: 'Automated Cancellation: 3 Unattended Calls'.
  • Patient Transparency: When a ticket expires or is cancelled, the exact audit reason is displayed on the patient's mobile tracker alongside a direct call-to-action to re-register at the triage desk.
Q9: How do you separate Nurse Intake Assessment from Doctor Clinical Advice in the database? Database Design

"Initially, all consultation notes were dumped into a single ConsultationNotes text field. This caused nurse triage observations to get overwritten by the doctor's final prescription.

To maintain medical audit integrity and HIPAA compliance:

  • Nurse Assessment: Stored in a dedicated TriageAssessments table linked to QueueTokenId, capturing CTAS Acuity (1–5), vital signs (BP, SpO2, HR, Blood Glucose), allergies, and nurse intake observations.
  • Doctor Documentation: Stored on the QueueToken as DoctorClinicalNotes and Prescription.
  • Audit Separation on UI: On the patient portal and historical views, the interface renders two distinct, clearly labeled cards: 'Nurse Intake Assessment' vs. 'Doctor Prescription / Clinical Advice'.
4. CTAS Emergency Triage & Prioritization Clinical Algorithms

Defending the priority calculation and anti-starvation mechanics.

Q10: What is the Canadian Triage & Acuity Scale (CTAS), and how is priority calculated? Algorithms

"CTAS is a standardized clinical classification system used in emergency medicine across 5 acuity levels:

  • Level 1 (Resuscitation): Immediate life threat (e.g., cardiac arrest, SpO2 < 85%). Target wait time: 0 minutes.
  • Level 2 (Emergent): Potential life/limb threat (e.g., chest pain, severe tachycardia HR > 130). Target wait time: < 15 mins.
  • Level 3 (Urgent): Moderate illness (e.g., high fever 39.5°C, mild respiratory distress). Target: < 30 mins.
  • Level 4 (Less Urgent): Mild pain, uncomplicated infection. Target: < 60 mins.
  • Level 5 (Non-Urgent): Minor symptoms, prescription refills. Target: < 120 mins.

When a nurse records vitals in VitalQ, the engine computes an Acuity Weight (Level 1 = 1000 pts, Level 2 = 500 pts, down to Level 5 = 10 pts). Patients with higher priority scores jump immediately to the top of the doctor's queue."

Q11: How do you prevent 'Starvation' where routine patients wait forever if emergency cases keep arriving? Queue Theory

"This is a classic Priority Inversion / Starvation problem in computer science. If you only serve higher-priority patients, routine Level 4 and Level 5 patients could wait indefinitely if Level 2 patients keep arriving throughout the day.

I solved this by implementing an Aging Algorithm:

EffectivePriorityScore = BaseAcuityWeight + (MinutesWaiting * AgingFactor)

For every 15 minutes a routine patient waits without being called, their score increments. Eventually, a routine patient who has been waiting for 90 minutes will age up and be served ahead of a newly arrived non-emergency case, guaranteeing timely care and bounded wait times."

Q12: How does the Nurse Re-Queue Protocol work for skipped patients? Workflow

"When a patient who was previously marked as Skipped returns to the clinic, the doctor cannot spend time finding them in the database.

The patient reports to the Nurse Triage Desk. The nurse uses the RequeuePatient workflow in nurse-dashboard.component.ts:

  1. The nurse reviews the patient's current vitals to ensure their clinical status has not deteriorated while waiting.
  2. The system resets the token status back to Waiting, clears the active skipped flag, but preserves the strike count history for audit accountability.
  3. A NotifyQueueUpdatedAsync SignalR broadcast immediately inserts the patient back into the doctor's active queue."
5. Security, Auth & Concurrency Control RxJS & Security

One of the most impressive technical bullet points on your resume.

Q13: Explain the RxJS Concurrency Mutex and why you built it. Advanced Angular

"This solves the infamous Token Refresh Race Condition in Single Page Applications (SPAs):

The Problem: When a user's 60-minute JWT expires, an Angular dashboard typically fires 4 to 6 parallel API requests simultaneously (e.g. fetching doctors, queue counts, metrics, notifications). If all 6 requests encounter a 401 Unauthorized at the same microsecond, each request independently triggers a /refresh-token call.

Because we use Refresh Token Rotation (each refresh token is single-use and immediately invalidated upon redemption), the 1st request succeeds and rotates the token. Requests 2, 3, and 4 arrive with the old refresh token, triggering a security violation on the backend that invalidates the session and logs the doctor out mid-consultation!

The Solution (RxJS Mutex): In my HTTP Interceptor, I created a concurrency mutex using a BehaviorSubject<string | null>:

private isRefreshing = false; private refreshTokenSubject = new BehaviorSubject<string | null>(null); // When a 401 is caught: if (!this.isRefreshing) { this.isRefreshing = true; this.refreshTokenSubject.next(null); // Lock mutex return this.authService.refreshToken().pipe( switchMap((newToken) => { this.isRefreshing = false; this.refreshTokenSubject.next(newToken); // Unlock mutex & broadcast new JWT! return next.handle(this.addToken(request, newToken)); }) ); } else { // Subsequent parallel requests WAIT until the mutex emits the new JWT! return this.refreshTokenSubject.pipe( filter(token => token !== null), take(1), switchMap(jwt => next.handle(this.addToken(request, jwt))) ); }

This guarantees that exactly one refresh request is made, while all other parallel requests pause and resume seamlessly with the new token."

Q14: Why did you run the 15-minute HIPAA auto-lock outside Angular's zone? Performance & Zone.js

"Under HIPAA Section 164.312, clinical terminals left unattended for 15 minutes must automatically lock to prevent unauthorized access to Protected Health Information (PHI).

To detect user inactivity, you must listen to global DOM events like mousemove, keydown, click, and scroll.

The Performance Trap: If you listen to mousemove inside the standard Angular zone (Zone.js), every pixel movement triggers Angular's dirty checking and change detection across the entire DOM tree! This destroys performance, causing browser lag and fan spin.

The Optimization: I injected NgZone and initialized the idle tracker using this.ngZone.runOutsideAngular(() => { ... }). The mouse listener resets an internal timer without triggering change detection. Only when the 15-minute timer expires do I re-enter the zone via this.ngZone.run(() => this.lockSession()) to display the lock screen."

Q15: How did you configure Rate Limiting in ASP.NET Core 8? API Security

"In Program.cs, I used the native .NET 8 Rate Limiting middleware (Microsoft.AspNetCore.RateLimiting).

Because the Public Token Tracker (/api/public/track) is accessible anonymously by patients holding paper slips without logging in, it was vulnerable to denial-of-service (DoS) enumeration attacks.

builder.Services.AddRateLimiter(options => { options.AddFixedWindowLimiter("PublicTrackerPolicy", opt => { opt.PermitLimit = 10; opt.Window = TimeSpan.FromMinutes(1); opt.QueueLimit = 2; }); });

If a script or malicious bot attempts more than 10 requests per minute from a single IP, the server immediately returns HTTP 429 Too Many Requests, protecting SQL Server from automated scrape attacks."

Q16: What is the difference between XSS and CSRF, and how does VitalQ protect against both? Web Security

"Cross-Site Scripting (XSS): An attacker injects malicious client-side JavaScript into the web page to steal cookies or session tokens.

Cross-Site Request Forgery (CSRF): An attacker tricks an authenticated user's browser into executing unauthorized actions on a vulnerable site where the user is currently logged in.

Defense in VitalQ:

  • XSS Defense: The Refresh Token is stored strictly inside an HttpOnly cookie, meaning client-side JavaScript cannot read or steal it even if an XSS vulnerability existed. Access tokens have short 60-minute lifetimes. Angular's built-in sanitizer automatically escapes dynamic data before rendering into the DOM.
  • CSRF Defense: The cookie is marked SameSite=Strict and Secure=true. Browsers refuse to attach the cookie to cross-origin requests. API mutation endpoints validate the custom Authorization: Bearer header, which cannot be forged via cross-origin form posts.
6. Entity Framework Core & Database Optimization SQL Server

Deep-dive technical questions on ORM bottlenecks, indexing, and memory allocation.

Q17: What is the N+1 query problem, and how did you prevent it in VitalQ? EF Core Performance

"The N+1 query problem occurs when an ORM executes 1 query to fetch a parent entity list, and then executes N additional individual queries to fetch child relationships for each item inside a loop.

In VitalQ: When loading the doctor's active queue, fetching 20 tokens without eager loading could trigger 20 additional round-trips to load patient details, vitals, and department info!

Prevention:

  1. Eager Loading: Used .Include(t => t.Patient).Include(t => t.TriageAssessment) so EF Core generates a single SQL LEFT JOIN.
  2. Projection via .Select(): Rather than loading entire tracked entity models into memory, I projected directly into lightweight DTOs (e.g. QueueTokenResponse). SQL Server retrieves only the required columns, cutting network payload size by 70%.
Q18: Why did you use .AsNoTracking() on read queries, and what memory benefit does it provide? EF Core Memory

"By default, Entity Framework Core creates a duplicate snapshot of every retrieved entity inside its internal Change Tracker so it can detect changes when SaveChangesAsync() is called.

For read-only operations — such as public ticket tracking, nurse queue views, and admin dashboards — tracking is completely unnecessary overhead.

Benefit: Adding .AsNoTracking() disables identity resolution and snapshot tracking:

  • Reduces .NET heap garbage collection allocations by 50%.
  • Executes queries up to 30% faster.
  • Prevents memory leaks in high-frequency background polling or WebSocket broadcast handlers.
Q19: What is a Filtered B-Tree Index, and why did you use it on RefreshToken? SQL Indexing

"A Filtered Index is a non-clustered index that includes a WHERE predicate to index only a specific subset of rows in a table.

In VitalQ, out of 100,000 registered patient records, only a small fraction (e.g. 500 active doctors, nurses, and logged-in patients) have an active refresh token at any given moment. 99% of rows have RefreshToken = NULL.

If you create a standard non-clustered index on RefreshToken, the B-Tree must store 100,000 pointers, wasting valuable buffer pool RAM and slowing down every patient registration insert.

CREATE UNIQUE NONCLUSTERED INDEX [IX_Users_RefreshToken] ON [Users] ([RefreshToken]) WHERE [RefreshToken] IS NOT NULL;

This filtered index is 99% smaller, stays permanently cached in L1/L2 server memory, and executes token validation seeks in < 0.2 milliseconds with zero table scans."

Q20: What is a Covering Index, and what is the difference between an Index Seek and an Index Scan? SQL Theory

"An Index Scan traverses every single page in the index tree from start to finish (an O(N) operation), which is slow and disk-intensive.

An Index Seek uses the B-Tree hierarchy (root page → branch page → leaf page) to jump directly to the exact memory address of the row using binary search (an O(log N) operation).

A Covering Index is an index that contains all the columns needed by a query. By using the INCLUDE clause:

CREATE NONCLUSTERED INDEX [IX_QueueTokens_DoctorId_Status] ON [QueueTokens] ([DoctorId], [Status]) INCLUDE ([TokenNumber], [CalledAtUtc], [CreatedAtUtc]);

SQL Server satisfies the query entirely from the index leaf pages without performing expensive Key Lookups against the clustered index."

Q21: How do you handle Database Transactions when calling or completing a patient? ACID Compliance

"When a doctor completes a consultation, multiple database operations must succeed atomically:

  1. Update the active token's status to Completed and record CompletedAtUtc.
  2. Persist the doctor's clinical advice and prescription text.
  3. Update the physician's daily completed consultation counter.

I wrap these operations inside an explicit Entity Framework Core transaction using using var transaction = await _context.Database.BeginTransactionAsync(). If any step fails (e.g. disk write failure), the transaction rolls back cleanly, maintaining 100% ACID compliance and preventing corrupted partial records."

Q22: Explain signal(), computed(), and effect() with actual examples from VitalQ. Angular 19 Signals

"Angular 19 Signals provide fine-grained reactivity without Zone.js overhead:

  • signal(): A reactive state container holding a value. In doctor-dashboard.component.ts:
    currentToken = signal<QueueToken | null>(null);
    When currentToken.set(newPatient) is called, Angular updates only the specific DOM nodes that read this signal!
  • computed(): A memoized deriving signal that recomputes only when its dependent signals change:
    patientsAheadCount = computed(() => { return this.queue().filter(t => t.status === 'Waiting').length; });
  • effect(): An operation that runs side-effects when signals change:
    effect(() => { const token = this.token(); if (token?.status === 'Called') { this.playAudioChime(); } });
Q23: Why Standalone Components and OnPush Change Detection? Architecture

"Standalone Components (standalone: true): Eliminates bloated NgModule files. Each component directly imports only the specific directives and modules it needs (e.g. CommonModule, FormsModule), enabling aggressive webpack tree-shaking and route-level lazy loading (cutting initial bundle size to under 110kB).

ChangeDetectionStrategy.OnPush: By default, Angular runs dirty checking across the entire component tree on every browser event. With OnPush, Angular only checks the component when an @Input() reference changes or a signal() notifies it, delivering buttery-smooth 60fps UI rendering even on low-powered hospital tablets."

Q26: Explain Dependency Injection Lifetimes in ASP.NET Core with examples from VitalQ. .NET Core DI

"ASP.NET Core provides three service lifetimes in Program.cs:

  • Transient (AddTransient): A new instance is created every time it is requested. Used for lightweight, stateless utility helpers.
  • Scoped (AddScoped): A single instance is created once per HTTP request lifecycle and shared across all services handling that request. In VitalQ:
    builder.Services.AddScoped<IQueueService, QueueService>(); builder.Services.AddScoped<IQueueNotificationService, QueueNotificationService>(); builder.Services.AddDbContext<AppDbContext>();
    AppDbContext must be Scoped to ensure all queries within a single HTTP request participate in the same transaction.
  • Singleton (AddSingleton): A single instance is created when the application starts and shared across all users and requests for the lifetime of the application. Used for in-memory caches, rate-limit state trackers, and background hosted services.
Q27: How do you extract the authenticated Doctor's ID from JWT Claims in the controller? Security & Claims

"A major security flaw in amateur APIs is trusting a client-supplied query parameter (e.g. ?doctorId=...) or request body field, allowing Doctor A to tamper with Doctor B's queue!

In VitalQ, the doctor's identity is extracted cryptographically from the signed JWT Claims in DoctorController.cs:

protected Guid GetCallerUserId() { var claim = User.FindFirst(ClaimTypes.NameIdentifier)?.Value; if (string.IsNullOrEmpty(claim) || !Guid.TryParse(claim, out var userId)) { throw new UnauthorizedAccessException("Invalid authentication token."); } return userId; }

The backend verifies the HMAC-SHA256 signature, ensuring the caller can only manipulate queues belonging to their own verified identity."

Q28: How did you implement Global Exception Handling in .NET 8? Error Handling

"Rather than wrapping every single controller action in messy try-catch blocks, I implemented global error handling adhering to RFC 7807 ProblemDetails:

Using custom middleware (or .NET 8's IExceptionHandler), unhandled exceptions are intercepted at the root:

  • KeyNotFoundException → Returns HTTP 404 Not Found with clean JSON message.
  • ArgumentException / ValidationException → Returns HTTP 400 Bad Request with field errors.
  • UnauthorizedAccessException → Returns HTTP 401 Unauthorized.
  • Any unexpected runtime crash → Logged securely to Serilog, returning HTTP 500 Internal Server Error without leaking sensitive stack traces or SQL connection strings to the public client.

Q29: If 50 hospitals adopt VitalQ tomorrow, how would you scale the system? System Design

"To scale VitalQ to handle 50+ hospital networks:

Q30: What happens if two doctors simultaneously call the same patient? How do you prevent race conditions? Concurrency Control

"In VitalQ, this is prevented at both the business logic and database transaction levels:

  • Optimistic Concurrency Control: Every QueueToken has a RowVersion (timestamp) column. When Doctor A calls the patient, the status changes to Called and the version increments. If Doctor B's request arrives concurrently, Entity Framework throws a DbUpdateConcurrencyException, which is caught and returned as a friendly 409 Conflict: 'Patient has already been summoned by another doctor.'
  • Atomic State Transitions: In the service layer, the token status transition query is conditional: WHERE Id = @TokenId AND Status = 'Waiting'. Only the first transaction modifies a row; the second updates 0 rows and returns early.

Outbox Pattern & RabbitMQ: Instead of publishing SignalR notifications directly inside the HTTP request thread, I would write events to an Outbox table and let a background worker publish them to a message broker (RabbitMQ/Kafka). This guarantees zero message loss even if the WebSocket service restarts during a database write.
  3. Tailwind Component Library: I would abstract reusable medical UI components (Vitals badges, CTAS pills, strike counters) into a dedicated shared UI library for faster feature delivery.
